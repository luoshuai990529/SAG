# SAG fnOS Docker 应用改造说明

- 输出时间：2026-07-30 09:41:20 CST（Asia/Shanghai）
- 对应分支：`feat/fnos-docker-app`
- 对应提交：`6c6a084232dd150de6d355dfc883b63b8282e4b8`
- 候选版本：`1.4.0-fnos.1`
- 当前支持平台：x86-64 fnOS

## 一、容器架构调整

1. **将 SAG 拆分为 API、Web 和 Nginx Gateway 三个容器，并只通过 Gateway 暴露宿主机端口 `3080`。**
   - 目的：隐藏 API `8000` 和 Web `3000` 内部端口，形成符合 fnOS Docker 应用形态的单一访问入口。

2. **为 Web 新增 `NEXT_PUBLIC_API_BASE=/` 同源访问约定，同时保留原有本地双端口开发方式。**
   - 目的：让浏览器在 fnOS 中通过同一域名和端口访问页面与 API，避免额外配置跨域地址。

3. **新增 Nginx 对页面、REST、SSE 和 MCP 请求的统一反向代理规则。**
   - 目的：保证普通接口、流式问答、MCP、文件上传和长耗时请求均能通过 `3080` 正常工作。

4. **统一保留 `Host`、客户端地址和转发协议等代理头，并关闭 SSE/MCP 响应缓冲。**
   - 目的：保持服务端对原始请求信息的正确识别，并避免流式响应被 Nginx 缓冲后延迟返回。

5. **为 4 GB 轻量 fnOS 环境固定任务并发、文档抽取并发、缓存和预热参数。**
   - 目的：降低默认资源占用，减少测试机和低内存 NAS 出现 OOM 的风险。

## 二、生产配置与认证调整

6. **fnOS 运行环境固定使用生产模式、关闭 Debug、关闭任意来源 CORS，并禁止初始化后的继续注册。**
   - 目的：避免开发配置、调试信息和开放注册能力进入局域网生产部署。

7. **新增 fnOS 专用密码认证模式，首次初始化必须使用独立 bootstrap 凭据设置密码。**
   - 目的：解决原有仅凭用户名即可取得登录令牌的问题，防止同一局域网中的其他客户端接管账号。

8. **为用户会话新增持久化认证版本，并在密码初始化或本地恢复时撤销旧 JWT。**
   - 目的：确保升级前无密码令牌和密码重置前的旧会话不能继续访问系统。

9. **新增本地停服密码恢复命令，并以一次性 bootstrap、双重容器状态检查和持久化写入完成安全重置。**
   - 目的：在不提供远程无限重置接口的前提下，为 fnOS 管理员保留可审计的账号恢复能力。

10. **将 bcrypt 计算移出异步事件循环，并增加错误账号的等价校验、登录限流和密码长度边界。**
    - 目的：降低用户名时序探测、并发暴力尝试和同步密码计算阻塞 API 的风险。

11. **由安装生命周期脚本生成互不相同的会话密钥和 bootstrap 凭据，并以 `0600` 权限原子保存。**
    - 目的：避免弱密钥、固定密钥、日志泄露和升级时意外覆盖既有会话密钥。

## 三、fnOS 应用包调整

12. **在 `packages/fnos/sag/` 下新增符合 fnOS 官方 Docker 模板的 Manifest、资源、UI、向导和生命周期目录。**
    - 目的：使 SAG 可以由 `fnpack` 构建为 fnOS 可识别、可安装和可管理的 `.fpk` 应用。

13. **Manifest 固定应用名 `sag`、版本 `1.4.0-fnos.1`、x86 平台、最低系统版本和服务端口 `3080`。**
    - 目的：让应用中心、桌面入口、端口检测和 Docker 资源使用一致的应用元数据。

14. **将 `${TRIM_PKGVAR}/data` 整体挂载到 API `/data`，并将冷备归档存放到 `${TRIM_PKGVAR}/backup`。**
    - 目的：把 SQLite、LanceDB、上传原文和索引作为不可拆分的数据边界统一持久化与恢复。

15. **安装流程支持私有目录初始化、随机密钥生成、旧环境文件补齐和重复执行幂等。**
    - 目的：保证首次安装、重装和版本升级不会破坏既有数据或覆盖合法密钥。

16. **状态检查同时验证 Gateway 容器状态、Gateway 健康和 API readiness。**
    - 目的：避免仅凭容器存在就错误地把不可访问或数据库未就绪的应用报告为正常。

17. **升级前执行完整停服冷备、空间预检、临时归档和同目录原子发布，成功后保持旧应用停止。**
    - 目的：保证升级包替换期间数据不再变化，并在空间或备份失败时于修改数据前安全终止。

18. **卸载默认保留数据，只有用户明确选择删除时才执行受控清理，并提供共享目录保留副本方案。**
    - 目的：防止误卸载造成知识库丢失，并兼容 fnOS 可能清理应用私有目录的行为。

19. **新增受限 lifecycle helper 容器处理 root-owned 数据的备份、删除、认证恢复和文件持久化。**
    - 目的：解决 fnOS 回调用户无法读取容器创建的 `0600` 文件问题，同时避免给宿主回调授予过宽权限。

20. **lifecycle helper 采用禁网、只读根文件系统、`no-new-privileges`、最小挂载和最小 capabilities。**
    - 目的：将 root helper 的访问范围限制在当前操作所需的数据、备份或配置目录。

21. **所有生命周期 Compose 命令显式固定 `--project-name sag` 和目标 Compose 文件。**
    - 目的：防止环境变量 `COMPOSE_PROJECT_NAME` 将升级、备份、恢复或删除操作重定向到其他项目。

22. **生命周期脚本在任何 Docker 或数据修改前验证路径规范性、符号链接、所有权和可替换边界。**
    - 目的：避免通过替换数据目录或备份目录把 root helper 的挂载和删除范围引向应用目录之外。

## 四、镜像构建与发布调整

23. **新增 GitHub Actions 多架构构建流程，为 API 和 Web 构建 `linux/amd64` 与 `linux/arm64` 镜像。**
    - 目的：满足当前 x86 fnOS 候选版运行需求，同时提前验证 ARM64 镜像的可构建性和元数据。

24. **镜像发布采用唯一 staging 标签、原始 OCI 索引检查和服务端 digest promotion。**
    - 目的：避免未经检查的镜像直接占用候选标签，并使失败后的同 digest 部分发布可以安全重试。

25. **最终 API/Web staging digest 会在 amd64 Runner 上真实启动并完成认证、readiness 和页面冒烟。**
    - 目的：确保被提升为候选版本的精确镜像就是实际运行验证过的镜像，而不是另一次独立构建。

26. **Web 冒烟会从精确 Web 容器的 `/app/.next/static` 选择真实构建产物并通过 HTTP 请求验证。**
    - 目的：证明候选镜像能够实际提供自身生成的 Next.js 静态资源，避免仅凭任意 HTML 或重定向判定成功。

27. **发布流程固定仓库、默认分支、候选版本、Commit SHA、Action 完整 SHA 和最小 GitHub 权限。**
    - 目的：防止从未审查分支发布同名候选版本，并降低具有 `packages:write` 权限的供应链风险。

28. **发布状态机对最终四个标签执行“缺失则创建、同 digest 接受、异 digest 拒绝”和发布后复核。**
    - 目的：保证候选标签不会静默改写其他内容，并能在部分标签创建成功后继续安全恢复。

## 五、镜像固定与网关安全调整

29. **`.fpk` Compose 只允许 API、Web 和 Nginx 使用不可变 digest，拒绝 `latest`、`build:` 和宿主 API/Web 端口。**
    - 目的：确保安装包在不同时间拉取到相同镜像，并阻止开发配置进入正式包。

30. **API/Web digest 必须与 `1.4.0-fnos.1` 候选标签绑定，并包含要求的 amd64/arm64 OCI 平台。**
    - 目的：防止把其他版本或缺失目标架构的镜像误装入 fnOS 候选包。

31. **Nginx 更新为官方 `1.30.4-alpine` 并固定到审核过的 OCI index digest。**
    - 目的：替换存在已知高危漏洞的旧 `1.27-alpine` 网关镜像，并保证网关来源可追溯。

32. **新增 Nginx 网关安全策略，绑定官方标签、index digest、平台子 digest、上游 revision 和 Trivy 报告 Target。**
    - 目的：防止构建器使用任意 Nginx digest 或伪造与受审镜像无关的漏洞扫描证据。

33. **发布前使用校验和固定的 Trivy 扫描精确 Nginx amd64 digest，并以可修复 High/Critical 为阻断条件。**
    - 目的：在候选镜像进入 staging 前阻止已存在修复方案的严重网关漏洞。

34. **Trivy 策略使用精确 UTC 时间戳和最长 30×24 小时有效期，报告异常时生成失败证据并阻断发布。**
    - 目的：防止过期漏洞结论继续使用，也避免扫描器异常或报告损坏被误记为零漏洞。

## 六、质量保障与文档调整

35. **新增 fnOS Compose、生命周期、打包、发布、认证、网关策略和运维文档的自动化测试。**
    - 目的：让端口、digest、密钥、备份顺序、路径权限和发布状态机等约束能够在改动后自动回归。

36. **新增 Mac 准备、网络安装、备份升级恢复、故障排查和证据型验收矩阵。**
    - 目的：为 Mac 开发、Windows VMware 转发和 fnOS 管理员操作提供可重复的执行与取证方法。

37. **文档明确 `appcenter-cli` 运行在 fnOS 设备上，而不是 Mac 的必装工具。**
    - 目的：修正早期评估中的工具定位错误，避免在开发机安装无用组件。

38. **文档将当前测试地址与通用可配置示例分开，并限定 HTTP `3080` 只用于可信隔离 LAN 或受控 VPN。**
    - 目的：避免把测试环境 IP 固化为产品配置，并明确未配置 HTTPS 时的安全使用边界。
